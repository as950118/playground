# JBOD(1브로커-N디스크) vs 브로커 확장(N브로커-N디스크)

카프카 클러스터의 저장 공간을 늘리는 방법은 두 축으로 나뉩니다. 서로 다른 문제를 해결하므로 우열이 아니라 트레이드오프로 이해해야 합니다.

## 1브로커 - N디스크 (JBOD)

브로커 하나에 디스크(로그 디렉터리) 여러 개를 등록하는 구성입니다.

```yaml
KAFKA_LOG_DIRS: /var/lib/kafka/data1,/var/lib/kafka/data2
```

- **장점**: 브로커(노드) 수를 늘리지 않고 저장 용량/디스크 처리량만 확장. 관리할 머신이 적어 비용 효율적.
- **단점**: 그 브로커가 떠 있는 VM/컨테이너 자체가 죽으면 디스크가 몇 개든 상관없이 그 브로커는 통째로 사라집니다. **장애 격리 단위는 여전히 브로커 하나**입니다.
- 새 파티션은 등록된 로그 디렉터리에 라운드로빈으로 배정됩니다. 파티션이 어느 디스크에 있는지는 `kafka-log-dirs.sh --describe`로 확인 가능.

### 실측 결과

3개 파티션(RF=3) 토픽을 만들고 각 브로커의 `data1`/`data2` 배정을 확인한 결과:

```json
broker 1: data1 → [kakao-0, kakao-2], data2 → [kakao-1]
broker 2: data1 → [kakao-1, kakao-2], data2 → [kakao-0]
broker 3: data1 → [kakao-1, kakao-2], data2 → [kakao-0]
```

모든 브로커에서 파티션 복제본이 두 디스크에 고르게 나뉘어 저장됨을 확인했습니다.

## N브로커 - N디스크 (Scale-out)

브로커를 여러 대로 늘리고, 각 브로커가 자기 디스크를 갖는 구성. 이 저장소의 기본 3노드 클러스터가 여기 해당합니다.

- **장점**: 노드 하나가 죽어도 나머지가 리더를 이어받아 서비스 지속 (실제로 [루트 README 3번 섹션](../README.md)에서 `docker stop kafka-2` 후 리더가 재선출되는 걸 확인함). 네트워크 대역폭도 노드 수만큼 병렬로 늘어남.
- **단점**: 관리 포인트 증가(패치, 모니터링, 브로커 간 리밸런싱 트래픽), VM 오버헤드로 스토리지 단가는 JBOD보다 비쌈.

## 결론: 실무는 둘을 섞는다

브로커는 여러 대(N)로 두어 노드 장애를 견디게 하고, 브로커 한 대당 디스크는 여러 개(JBOD)를 붙여 그 브로커의 용량/처리량을 늘리는 **"N브로커 × N디스크"** 조합이 표준 프로덕션 패턴입니다. 이 저장소의 최종 구성(`docker-compose.yml`)이 정확히 이 형태입니다 — 브로커 3대, 브로커당 디스크 2개.
